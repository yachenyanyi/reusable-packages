# 代码库扩展策略

## 复杂度目标

让新增数据场景、替换统一采集 API、接入现有平台和独立运行都只影响局部代码；调用者不需要理解重试、游标、回退、版本比较和事务顺序。

## 两种候选设计

### 方案 A：所有能力都做成统一平台核心

核心同时拥有用户、任务、调度、采集、分析、报告和通知。开箱能力多，但任何项目都必须接受整套模型；接入已有平台时容易出现两套用户、权限和套餐体系。

### 方案 B：小而稳定的核心，加可选扩展和宿主适配

核心只拥有可靠运行与内容历史；任务、分析和交付能力按需装配；用户与套餐留给宿主。公共接口更小，独立运行也不需要伪造平台概念。

选择方案 B。代价是项目启动时需要一个 composition root 明确装配哪些扩展和适配器，但这正是不同项目应该承担的差异。

## 扩展方式

### 新增数据场景

新增场景映射，把场景请求转成 `RunRequest`，把上游记录转成 `Observation`。不修改采集状态机和内容历史。

### 新增上游提供方

实现 `UpstreamJobGateway`。供应商状态、错误码、Webhook 和分页字段被封装在适配器内。

### 新增分析能力

消费 `ChangeEvent` 或查询快照，产生扩展自己的结果。分析失败不回滚已完成的采集和历史记录。

### 接入现有平台

增加 host integration，把平台的身份、任务、套餐计算和调度映射为核心上下文与请求。核心不导入平台代码。

### 独立运行

使用本地配置、固定 `scope_key`、轻量调度器和 SQLite/PostgreSQL 适配器装配同一个核心，不需要用户与套餐模块。

## 暂不抽象

- 不设计通用插件市场和动态插件协议。
- 不设计万能工作流或规则语言。
- 不为未知供应商统一所有配置字段。
- 不把每个类都拆成接口；只有跨边界且存在替换原因的能力才定义端口。
- 不承诺 `Item`、`Attempt`、游标检查点和 ORM 模型为公共 API。

## 测试门槛

- 核心契约测试：状态、幂等、隔离和变化事件语义。
- 网关适配器契约测试：提交、终态、分页、重复结果、错误分类和取消。
- 内容历史测试：身份稳定、重复观察、版本变化、失联与恢复。
- 运行恢复测试：进程在提交后、分页中和写入后中断，恢复后不丢不重。
- 装配测试：同一核心分别用本地适配器和平台适配器运行最小闭环。

## 评审规则

未来每加一个扩展点，都先回答：它是否已经有两个真实变化来源；是否隐藏了复杂知识；不做接口时会修改几个模块。回答不清楚，就先保留为模块内部实现。
