# 代码目录与扩展布局

## 设计目标

新增业务场景、上游采集提供方、数据库或宿主平台时，主要通过增加一个目录完成；核心模块不反向导入扩展。第一阶段保持单仓库、单发布包，等出现独立版本或依赖隔离需求后再拆包。

## 候选方案

### 方案 A：按技术层全局分目录

```text
models/ services/ repositories/ controllers/ utils/
```

一个 GEO 功能会散落在多个目录，删除或抽取它时需要跨仓库寻找；`services` 和 `utils` 很容易变成无边界的公共区域。

### 方案 B：按稳定核心、扩展类型和装配边界分目录

每个业务扩展把自己的契约、采集适配和内容策略放在一起；技术产品适配器与业务扩展分开；最终由应用装配目录选择组合。

选择方案 B。目录表达所有权和依赖方向，而不只是代码执行顺序。

## 四种新增需求放在哪里

### 新业务场景

例如价格监测放入：

```text
extensions/price/
├─ contracts.py              # PriceScanSpec、PriceObservationContent
├─ collection_adapter.py     # 实现 CollectionAdapter
├─ content_policy.py         # 实现 ContentPolicy
└─ __init__.py               # 只导出该扩展的装配入口
```

站点、GEO 和舆情也遵循相同结构，但不要求完全相同的内部文件。简单扩展可以合并文件，避免为形式统一制造浅模块。

### 新采集 API 或供应商

放入 `adapters/upstream/<provider>/`，实现核心拥有的 `UpstreamJobGateway`。供应商鉴权、状态码、Webhook、游标和 DTO 都留在这个目录。

### 新数据库或对象存储

分别放入 `adapters/persistence/<technology>/` 和 `adapters/artifacts/<technology>/`。迁移脚本与 ORM 映射跟随具体适配器，不进入 `contracts/` 和核心领域模型。

### 新宿主平台或客户项目

- 可复用的平台映射放在 `integrations/<platform>/`。
- 项目专属配置和装配放在 `apps/<project>/`。
- 客户专属规则先留在项目 app；经过第二个真实项目验证后，再提炼到 `extensions/`。

## 依赖方向

```text
                   ┌→ integrations ─┐
apps（装配入口） ───┼→ extensions ───┼→ contracts / collection / history
                   └→ adapters ─────┘                 ↑
                                                       │
                                   核心只声明端口，不导入实现
```

`integrations` 可以按需要使用稳定扩展能力；`extensions` 和 `adapters` 不互相依赖。`adapters` 在代码依赖上导入核心端口，应用装配层再把适配器实例交给核心。核心永远不能通过包路径查找或导入具体适配器。

## 扩展装配方式

第一版采用显式装配，不做自动扫描：

```text
应用 composition root
  ├─ 选择 CollectionAdapter
  ├─ 注册 ContentPolicy
  ├─ 选择 UpstreamJobGateway
  ├─ 选择 State/History/Artifact 实现
  └─ 构建 MonitoringKit
```

显式装配更容易看清一个项目实际启用了什么，也避免导入模块时产生隐式注册副作用。未来确实需要第三方扩展时，可以把同一装配入口发布为独立包，而不改变核心契约。

## 可选依赖

- 核心只依赖标准库和少量稳定基础依赖，不引入 Web 框架、ORM、队列或供应商 SDK。
- PostgreSQL、S3、LLM、具体平台客户端等依赖跟随相应适配器，通过安装 extras 或后续独立包选择。
- 扩展目录的 `__init__` 不应因为被扫描就导入重型 SDK 或建立网络连接。
- 缺少某个可选依赖时，只影响对应适配器的装配，并给出明确错误；不能导致核心包无法导入。

例如将来可以提供类似 `monitoring-kit[postgres,s3]` 的安装组合，但 extras 名称属于发布设计，不进入领域契约。

## 不建议出现的目录

- 全局 `utils/`：工具应留在拥有其语义的模块内；真正通用后再提炼。
- 全局 `services/`、`managers/`：名称不表达所有权，容易形成上帝模块。
- 全局 `repositories/`：端口跟随拥有不变量的核心模块，具体实现放适配器。
- `plugins/` 大杂烩：业务扩展、技术适配器和宿主集成有不同变化原因，不能混放。
- `shared/models/`：容易让 ORM、API DTO 和领域契约互相污染。

## 何时拆成多个发布包

出现以下真实需求之一再考虑 `packages/monitoring-core`、`packages/monitoring-ext-geo` 等多包结构：

- 扩展需要独立版本和发布周期。
- 可选扩展带来明显的重型或冲突依赖。
- 其它仓库只需要安装某个扩展。
- 不同团队独立维护并需要明确兼容矩阵。

在此之前，多包只会增加构建、版本、发布和调试成本，不会自动带来更好的模块化。

## 边界检查

- 使用静态导入规则禁止 `collection/`、`history/` 导入 `extensions/`、`adapters/`、`integrations/`、`apps/`。
- 每个扩展和适配器必须通过相应契约测试套件。
- `monitoring_kit.__init__` 只导出承诺兼容的公共 API，内部类不从顶层导出。
- 项目 app 可以依赖所有已选模块，但其它模块不能依赖项目 app。
