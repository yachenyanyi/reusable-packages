# monitoring-kit v0.3 事务型 Outbox 开发计划

对应 GitHub Issue：[#3 为 ChangeEvent 引入事务型 Outbox 与可靠投递](https://github.com/yachenyanyi/reusable-packages/issues/3)。

## 1. 任务与状态

为已经提交的 `ChangeEvent` 增加可恢复的至少一次投递能力，消除“历史事务已经成功，但进程在事件发送前退出，导致下游永久收不到事件”的窗口。

本计划属于 `monitoring-kit` 的通用可靠性能力，但不是 v0.2 的前置条件。首轮实现已经在当前工作树完成，并已通过本地真实 MySQL 8.0.36 验收；正式发布或接入其它环境时仍需复跑关系型 schema、投递和恢复契约。

## 2. 当前基线

当前实现按投递保证等级分成两条路径：

```text
AT_LEAST_ONCE：
计算历史结果 → HistoryStore.commit(HistoryWrite + Outbox)
             → OutboxDispatcher.dispatch_once() → EventPublisher

NONE：
计算历史结果 → HistoryStore.commit(HistoryWrite)
             → 可选 EventSink 提交后直发
```

在 `AT_LEAST_ONCE` 路径中，`Document`、`Snapshot`、`ChangeEvent`、ingest 幂等记录和 Outbox 投递意图在同一历史事务中提交；传输失败只改变投递状态，不影响已经提交的历史事实。`NONE` 路径保留给轻量独立运行，直发失败不提供持久化投递保证。

## 3. 复杂度目标

- 调用方只表达“启用可靠事件投递”，不负责组织事务、领取、退避、确认和恢复顺序。
- `ContentHistory` 继续只负责历史事实，不感知 Kafka、RabbitMQ、Webhook 或数据库行。
- 传输失败只影响投递状态，不回滚或伪造已经提交的历史事实。
- SQLite、MySQL 和内存参考实现共享同一份投递语义，不复制业务算法。
- 保持 `ChangeEvent.event_id` 稳定，使下游可以幂等消费。

## 4. 方案比较

### 方案 A：让 EventSink 自己保存 Outbox

`ContentHistory` 在历史提交后调用一个具备持久化能力的 `EventSink`，由它保存并发送事件。

问题是 EventSink 与 HistoryStore 拥有两个独立事务。进程仍可能在历史提交后、Outbox 保存前退出，因此无法关闭丢事件窗口。若让调用方传递数据库事务，又会把持久化实现泄漏进核心。

### 方案 B：历史事务写入投递意图，独立 Dispatcher 发送

`HistoryStore.commit(HistoryWrite)` 在保存历史事实时，同事务追加待投递记录；独立 `OutboxDispatcher` 领取、发送并确认。`EventSink` 只代表传输边界。

选择方案 B。`HistoryWrite` 已经包含本次产生的事件，核心不需要认识 Outbox 表或数据库事务。关系型适配器可以在现有事务里原子追加记录，Dispatcher 则把重试和恢复复杂度藏在一个小接口后面。

## 5. 模块与接口设计

### 内容历史

- `ContentHistory.record()` 仍只接受一次 Observation 并返回 `HistoryResult`。
- 不再把“提交后立即调用 EventSink”当作可靠投递路径。
- `HistoryWrite.events` 是历史事实和待投递意图的唯一来源，不能由适配器重新推断。
- 同一 ingest key 重放不得生成第二条 Outbox 记录。

### 事件投递运行时

由一个深模块隐藏领取、续租、发送、确认、退避和崩溃恢复：

```text
OutboxDispatcher.dispatch_once(DispatchRequest) → DispatchSummary
```

宿主只负责按需调用 `dispatch_once` 或把它挂到自己的 Worker 循环。它不逐条协调 `claim → publish → ack`。

内部 SPI 可以包含：

```text
EventDeliveryStore.claim_pending(...)
EventDeliveryStore.mark_delivered(...)
EventDeliveryStore.reschedule(...)
EventSink.publish(events)
```

这些接口是 runtime 与 adapter 之间的 SPI，不进入顶层稳定公共 API。精确的租约 token、数据库版本和行结构均为适配器私有知识。

### 关系型适配器

Outbox 最少保存：

- 稳定 `event_id`，并建立唯一约束；
- 事件的版本化载荷；
- `pending / delivering / delivered` 投递状态；
- attempt 次数、下次尝试时间和最后一次可诊断错误；
- 领取租约与内部 fencing/version；
- 创建、最近尝试和成功时间。

Outbox 与 `ChangeEvent` 在同一个数据库事务写入。SQLite/MySQL 只在私有领取方言上不同，不复制整个 Store。

### 装配策略

可靠投递应通过有名称的策略表达，例如 `DeliveryGuarantee.NONE` 与 `DeliveryGuarantee.AT_LEAST_ONCE`，不使用含义模糊的 `enable_outbox=True`。

独立本地运行默认可以不启动 Dispatcher；启用至少一次投递时，装配层必须同时提供 EventSink 和 Dispatcher 的运行方式。不得同时配置“提交后直接发布”和“Outbox 发布”两条互相竞争的路径。

## 6. 投递语义

- 保证至少一次，不承诺恰好一次；消费者必须按 `event_id` 去重。
- 不承诺不同 Document 之间的全局业务顺序。
- 同一 Document 的事件优先按 `sequence` 发送，不能让后续事件长期越过失败的前序事件。
- EventSink 超时视为结果未知，记录保持可重试；不能因为可能重复就标记成功。
- 超过重试阈值后进入可观察的阻塞状态，不静默删除；是否人工重放属于后续运维接口。
- Dispatcher 崩溃后由租约过期恢复，旧 Dispatcher 不能确认新 Worker 已重新领取的记录。

## 7. 分阶段实施

### 阶段 0：schema 发布决策

- 确认已有数据库是否需要保留。
- 若需要保留，提升 `SCHEMA_VERSION` 并提供明确的 v1 → v2 前向迁移。
- 若全部是临时数据库，明确记录“需要重新初始化”，仍不能在同一 schema version 下静默改变表结构。

### 阶段 1：先建立失败测试

- 历史提交成功、EventSink 未执行时，待投递事件仍可恢复。
- 历史事务回滚时没有 Outbox 记录。
- 同一 ingest key 重放只产生一个 `event_id` 和一条待投递记录。
- 投递成功前终止 Dispatcher，租约过期后可以重新领取。
- 旧 Worker 不能确认已被新 Worker 重新领取的记录。

### 阶段 2：定义投递 SPI 与内存参考实现

- 定义最小 `DispatchRequest`、`DispatchSummary` 和可处理错误。
- 实现内存 EventDeliveryStore，用契约测试固定状态转换、重试和 fencing 语义。
- 已将可靠路径与提交后直发路径分开；`AT_LEAST_ONCE` 不允许同时配置直发 `EventSink`。

### 阶段 3：关系型 Outbox

- 在共享 schema 中增加 Outbox 表和索引。
- 修改 `RelationalHistoryStore.commit()`，在历史事务内追加投递记录。
- 实现 SQLite/MySQL 的原子领取和 CAS 确认。
- 复用现有安全错误翻译，不向核心泄漏数据库异常。

### 阶段 4：Dispatcher 与故障注入

- 实现有限批次 Dispatcher、退避和租约恢复。
- 在 commit 后、publish 前、publish 后 ack 前等位置注入进程中断。
- 验证重启后事件最终可达，且重复投递保持同一 `event_id`。

### 阶段 5：文档与 CLI 验收

- CLI 增加一次性 `dispatch` 测试入口，而不是内置永久守护进程。
- 文档展示“记录历史”和“投递事件”两个可独立运行的循环。
- 使用假 EventSink 验证临时失败、结果未知、恢复和消费者去重。

## 8. 测试矩阵

- memory：完整状态机、退避、重复投递和 fencing 契约。
- SQLite：事务原子性、多连接领取、进程恢复和 schema 升级。
- MySQL 8+：`SKIP LOCKED`/等价领取、多 Worker、旧租约围栏和大载荷往返。
- 集成流：Observation → History commit → Outbox → EventSink。

普通单元测试不需要真实消息中间件。第一版使用可控假 Sink 即可证明可靠性语义。

## 9. 非目标

- 不在本轮引入 Kafka、RabbitMQ、Celery 或通用消息总线。
- 不实现跨数据库与消息队列的分布式事务。
- 不承诺恰好一次投递。
- 不加入业务通知模板、订阅关系或预警规则。
- 不把任意内部事件全部塞进 Outbox；只处理已经承诺的稳定事件。

## 10. 完成标准

- 历史事实和待投递记录原子提交。
- 任意投递窗口崩溃后都能恢复，且不存在永久丢失窗口。
- 至少一次语义、重复处理责任和顺序边界写入接口文档。
- memory、SQLite 和真实 MySQL 运行同一份关键契约测试。
- 调用方不接触事务、行锁、重试次数、租约 token 或数据库载荷。
- 核心不依赖 SQLAlchemy、数据库表或消息供应商。
