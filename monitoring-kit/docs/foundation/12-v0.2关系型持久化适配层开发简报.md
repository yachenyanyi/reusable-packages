# monitoring-kit v0.2 关系型持久化适配层开发简报

## 任务

为已经完成的 `monitoring-kit` 核心提供一套可在启动时选择 SQLite 或 MySQL 的关系型持久化适配层。它实现既有 `RunStateStore` 与 `HistoryStore` 端口，供独立 CLI、未来项目 app 或宿主平台在装配时使用。

本次只增加持久化实现和装配入口；不改变采集、内容历史的领域接口，不实现某个项目的业务模型、用户体系或任务中心。

## 当前状态

关系型适配层的首轮实现已经落在当前工作树：SQLite/MySQL 共用一套 Store，数据库类型由 `database_url` 选择，并已包含 schema v1 → v2 的基础升级路径、Run CAS、History 并发保护、scope 校验、分页下推和 Outbox 持久化支持。

本地已使用 MySQL 8.0.36、InnoDB 和 `utf8mb4` 完成多连接、多 Worker、锁恢复和大载荷契约测试；发布或接入其它环境时仍需按同一契约复跑。

## 复杂度目标

- 调用方只提供一个数据库连接串，并得到一组可用 Store；不需要判断数据库类型、管理连接或分别构造两个 Store。
- 核心继续只依赖 `RunStateStore`、`HistoryStore`，不知道 SQL、ORM、连接、表名、锁、事务与方言。
- SQLite 与 MySQL 的共同语义只实现一次；并发领取等真实不同的地方留在私有方言实现中。
- 未来新增关系型数据库或替换迁移工具时，影响局限在适配器内部，而不是扩散到核心和业务扩展。

## 现有端口与边界

`collection.ports.RunStateStore` 已表达运行状态所需的能力：按幂等键查询、创建和保存 Run、领取可运行 Run、列出未完成 Run。`history.ports.HistoryStore` 已表达内容历史所需的能力：按 `ingest_key` 去重、读取 Document/当前版本/时间线、原子提交历史写入和查询变化事件。

这两个端口是稳定边界。关系型实现可以导入领域模型和端口，但以下内容不得穿过边界：

- SQLAlchemy 对象、SQL 文本、数据库行、连接、Session、表名、方言能力；
- 数据库异常、锁冲突错误、连接串和用户名密码；
- SQLite/MySQL 专有字段或事务使用方式。

适配器应把可恢复的基础设施失败翻译为稳定的持久化错误；不能安全处理的失败保留原因链，但异常文本必须不含原始连接串或密码。

## 候选设计

### 方案 A：SQLite 和 MySQL 各自实现一整套 Store

优点是直观。问题是编码、schema、历史事务、查询语义和测试会复制两遍；未来修复幂等或历史一致性问题时，很容易只修一个数据库。

### 方案 B：把 `backend=sqlite/mysql`、连接和方言分支交给核心

优点是可以少写一个装配模块。问题是核心会依赖数据库产品，并且调用方要理解数据库差异；这破坏端口的隔离作用。

### 方案 C：一个关系型深适配器，内部保留私有方言策略

公共装配入口根据 `database_url` 选择驱动和方言，适配器统一拥有 schema、编码、普通读写、事务与错误翻译。只有并发领取等无法共享的细节放入私有 `dialects/`。

选择方案 C。它把“如何在不同关系型数据库中保持同一 Store 语义”收进一个深模块，不给核心和调用方增加协调负担。

## 装配契约

建议在 `monitoring_kit.adapters.persistence.relational` 暴露最小装配 API：

```text
PersistenceConfig(database_url, ...)
open_persistence(config) -> PersistenceBundle

PersistenceBundle
├─ run_state_store: RunStateStore
├─ history_store: HistoryStore
└─ close() -> None
```

`PersistenceConfig` 的数据库选择权只来自 `database_url`，例如 SQLite 文件 URL 或 MySQL URL；不再额外引入会与 URL 冲突的 `backend` 参数。配置可包含连接池、超时和 schema 初始化等装配选项，但不暴露给领域核心。

`PersistenceBundle` 是组合根使用的生命周期对象：它确保两个 Store 使用同一数据库基础设施，并集中关闭连接池。它不是新的领域服务，也不在 `monitoring_kit.__init__` 顶层导出。

调用方应在 composition root 创建一次 bundle，把其中的 Store 注入 `CollectionEngine` 和 `ContentHistory`，并在进程关闭时调用 `close()`。

## 建议目录

```text
src/monitoring_kit/adapters/persistence/
├─ memory.py                         # v0.1 已有参考适配器
└─ relational/
   ├─ __init__.py                    # PersistenceConfig、open_persistence、PersistenceBundle
   ├─ bundle.py                       # 生命周期与组合
   ├─ schema.py                       # 元数据、schema 版本、前向升级
   ├─ codecs.py                       # 领域契约与关系型记录之间的私有转换
   ├─ run_state_store.py              # RunStateStore 实现
   ├─ history_store.py                # HistoryStore 实现
   ├─ transaction.py                  # 关系型写事务生命周期
   ├─ errors.py                       # 脱敏后的稳定基础设施错误
   └─ dialects/
      ├─ __init__.py
      ├─ sqlite.py                    # SQLite 的连接、事务和领取策略
      └─ mysql.py                     # MySQL 的连接、事务和领取策略
```

`codecs.py`、schema、SQL 和方言策略都是适配器私有知识，不能被核心、扩展或宿主直接导入。若将来需要 PostgreSQL，增加一个私有方言实现并通过相同语义测试；不创建第三套领域 Store。

## 一致性不变量

### 内容历史

一次 `HistoryStore.commit(write)` 必须处于单个数据库事务中。以下结果要么全部可见，要么全部不写入：

- Document 及其 current snapshot 指针；
- 本次产生的 Snapshot；
- 本次产生的 ChangeEvent；
- `ingest_key` 指纹和可重放 `HistoryResult` 的记录。

同一个 `scope_key + ingest_key` 的重复提交必须得到与首次相同的历史结果，不得产生第二个 Snapshot 或 ChangeEvent。

### 运行状态与历史之间

不建立跨 `RunStateStore` 和 `HistoryStore` 的全局事务。已有核心遵守安全顺序：先完成历史原子提交，再保存 Run/cursor。若进程在两者之间中断，恢复后的重复投递借助 `ingest_key` 幂等重放，不会重复制造历史事实。

这是有意识的边界：它避免为了两个概念不同的 Store 引入分布式事务或要求调用方协调事务。

### 领取与租约

`allocate(AllocationRequest)` 返回的 Run 必须被原子地标记为租约属于请求中的 worker。在多个 worker 并发调用时，同一 Run 在同一有效租约期间不能被重复领取。旧的 `claim_runnable(...)` 只作为兼容入口，内部转入同一分配语义。

领取算法是唯一允许明显按方言分化的地方。`ClaimStrategy` 如有必要，只能是 `relational/dialects/` 内部私有协作者，不能新增公开 SPI，也不能被核心选择。

## SQLite 与 MySQL 的运行假设

- SQLite 面向 CLI、开发、测试和低并发单机使用，正确性优先；并发写入能力有限。
- MySQL 面向 MySQL 8+、InnoDB、UTF-8 `utf8mb4`、UTC 时间和多个 worker 的服务部署。
- 两者必须通过同一份 Store 语义测试。具体锁语句、连接参数和事务细节由方言模块承担。

连接串永远不应进入 Telemetry、审计、日志或异常文本。`PersistenceConfig.safe_url` 仅可显示脱敏后的连接信息，密码必须被替换。

## Schema 与迁移

v0.2 新建 `monitoring_kit_schema_version`，记录当前 schema 版本。适配器必须能识别未初始化、支持的旧版本和不支持的未来版本；只允许定义明确的前向升级路径，不能静默猜测或降级。

Schema migration 与 SQLite 到 MySQL 的数据迁移是两件事：前者是同一数据库演进，后者是运行数据搬迁。v0.2 只提供前者的版本协议，不承诺自动跨数据库搬迁。Alembic 不是本次硬前提；第一次出现真实 schema 变更时，再根据迁移复杂度决定是否引入。

## 验证计划

- 对内存、SQLite、MySQL 运行同一组 `RunStateStore` 与 `HistoryStore` 语义测试。
- SQLite/MySQL 专有测试覆盖：关闭后重开、schema version、`safe_url` 脱敏、独立连接下的并发领取。
- SQLite 并发测试使用临时文件数据库，不能使用单连接内存数据库。
- 历史事务测试验证失败时不留下半个 Snapshot、ChangeEvent 或去重记录。
- 恢复测试验证“历史已提交、Run/cursor 尚未保存”的中断可由幂等重放安全恢复。
- 以 CLI 或最小装配样例验证仅替换 `database_url` 即可在 SQLite 与 MySQL 之间切换。

## 实现顺序

1. 定义装配 API、脱敏配置和稳定基础设施错误。
2. 实现共享 schema、codec 与 schema version 初始化/检查。
3. 实现关系型 `HistoryStore`，先锁定事务与幂等不变量。
4. 实现关系型 `RunStateStore` 和 SQLite/MySQL 私有领取策略。
5. 补齐共享契约测试、方言并发测试和 CLI 验收。
6. 在真实 schema 变更出现前，不引入额外迁移框架或通用数据搬迁器。

## 完成标准

- 装配层只通过 `database_url` 选择 SQLite/MySQL，调用方不接触方言分支。
- 核心与业务扩展没有 SQLAlchemy、表、连接、数据库异常或数据库类型依赖。
- 两个 Store 的关键语义在 SQLite 和 MySQL 上通过相同测试。
- 内容历史提交、幂等重放、Run 领取与连接串脱敏都有自动化验证。
- 文档清楚区分公开装配 API、内部方言细节、schema 迁移和跨库数据迁移。

## 非目标

- 不增加通用 Repository 基类或为每张表创建公开 CRUD API。
- 不把 MySQL/SQLite 选择、锁策略或事务对象提升为核心 SPI。
- 不实现 PostgreSQL、对象存储、外部队列或业务项目专用表。
- 不提前加入分布式事务、自动数据搬迁或 Alembic 强依赖。
