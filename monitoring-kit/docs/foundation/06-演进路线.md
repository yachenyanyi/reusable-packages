# 演进路线

演进目标是验证抽象，而不是一次性完成所有模块。

## 阶段 0：契约先行

- 明确领域语言、模块边界和最小接口。
- 确定一个真实场景作为验证样本。
- 建立架构决策和变更记录。

成功标准：团队能解释每个模块负责什么、不负责什么。

## 阶段 1：第一个最小闭环

选择站点监测、GEO 或舆情中的一个场景，只完成：

```text
Source → Task → Run → Observation → Snapshot → ChangeEvent
```

先不做复杂 AI、万能规则、微服务、多租户和平台套餐。

同时提供一个最简单的本地装配，证明核心不依赖现有平台也能独立运行。

## 阶段 2：第二个场景验证复用

接入与第一个场景明显不同的数据源。观察哪些接口不变、哪些抽象只是第一个项目的偶然细节。

只有经过第二个场景验证的能力，才正式提升为共享核心；否则继续留在场景模块。

## 阶段 3：分析与处置

- 引入可版本化的 AnalysisProfile。
- 增加 Finding、人工确认和 Case 状态机。
- 增加报告和有授权边界的预警。

## 阶段 4：运行强化

- 多 Worker、队列、来源级限速和熔断。
- 数据质量、运行指标和异常告警。
- 备份、归档、保留期限和灾难恢复。

## 阶段 5：宿主平台接入

通过平台适配层把 `scope_key`、`actor_ref`、`ExecutionLimits`、调度和通知映射到现有平台。用户、套餐、支付与权限继续由平台拥有，不搬进核心代码库。

## 每阶段复盘问题

- 哪个变化改动了不该改的模块？
- 哪个接口迫使调用者知道内部顺序？
- 哪些配置其实属于另一个模块？
- 哪些抽象只有一个使用者且没有隐藏复杂度？
- 哪个重复已经出现两次，值得在第三次前提炼？
