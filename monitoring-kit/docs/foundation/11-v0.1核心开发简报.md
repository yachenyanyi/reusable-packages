# monitoring-kit v0.1 核心开发简报

## 任务

根据现有架构和契约文档，完成 `monitoring-kit` 的第一版可运行核心：稳定数据契约、可靠采集运行、内容历史、扩展注册、统一采集 API 适配边界、参考内存适配器、CLI 黑盒验收入口和自动化测试。

本次只实现可复用核心，不实现站点、GEO、舆情的业务模型，也不实现用户、租户、套餐、权限、报告、预警和平台集成。

## 复杂度目标

- 隐藏上游 HTTP 协议、状态码、任务 ID、游标、事件重复和分页细节。
- 隐藏 Run、Item、Attempt 的状态推进、重试、退避、恢复和结果核对顺序。
- 隐藏 Document、Snapshot、ChangeEvent 的身份、哈希、版本和缺失确认规则。
- 让新增场景主要增加 `CollectionAdapter` 和 `ContentPolicy`，而不是修改核心状态机。
- 让同一个核心可以由 CLI 独立装配，也可以由未来宿主平台注入自己的存储和上游适配器。

## 候选设计

### 方案 A：一个总服务同时负责采集、历史、存储和上游 HTTP

- 接口：一个大对象暴露任务创建、轮询、结果写入和历史查询。
- 优点：文件少，初期看起来直接。
- 问题：上游协议、运行状态和历史规则互相污染；更换存储或加入回退会修改同一个上帝模块；无法清楚替换端口。

### 方案 B：按执行步骤拆成提交器、轮询器、解析器、重试器、仓储服务

- 接口：调用方依次协调各个步骤，并在步骤之间传递游标、Attempt 和临时数据。
- 优点：每个文件看起来很小。
- 问题：这是按时间顺序拆分，不是按隐藏知识拆分；调用方必须知道正确顺序，重试和恢复逻辑会重复，产生大量浅层转发接口。

### 方案 C：两个深核心模块加窄端口

- `CollectionEngine`：隐藏一次 Run 的完整推进、上游任务关联、重试、回退路由、游标和恢复。
- `ContentHistory`：隐藏身份解析后的 Document、Snapshot、ChangeEvent 推进和幂等。
- `ExtensionRegistry`：启动时显式注册采集适配器和内容策略。
- `UpstreamJobGateway`、运行状态端口、历史存储端口和事件端口：只表达核心真正需要的能力。
- 统一 API、内存网关和未来数据库实现放在适配器边界外侧。

选择方案 C。它的公共接口较小，但能承载真正复杂的执行和历史不变量。

## 选择的设计

### 最深模块

`CollectionEngine` 是执行方向最深的模块：调用方只需提交、取消、查询和唤醒，不需要自己轮询、推进游标、处理重复结果或安排重试。`ContentHistory` 是历史方向最深的模块：调用方只提交 `Observation`，不能直接创建 Snapshot 或 ChangeEvent。

### 公共 API

```text
submit_run(RunRequest, ExecutionContext) → RunRef
cancel_run(run_id, ExecutionContext)        → CancellationResult
get_run(run_id, scope_key)                  → RunSummary
query_changes(ChangeQuery, scope_key)      → ChangePage
```

运行宿主只额外使用：

```text
wake(limit)                 → WorkSummary
recover_interrupted_runs()  → RecoverySummary
```

`submit_run` 只接受请求并返回排队中的 Run；`wake` 是显式运行推进入口。CLI 通过循环调用 `wake` 验收，不在核心中偷偷创建后台线程。

### v0.1 的执行边界

- 一个 `RunRequest` 对应一个内部采集 Item 和一个上游任务；批量目标由场景适配器的任务规格表达。
- 上游提交使用内部 `run_id` 作为幂等键。提交响应不确定时只能用同一个键重试，不能贸然创建第二个上游任务。
- 传输失败、限流和暂时不可用使用指数退避；明确允许回退的提交失败才切换备用网关。已被上游接受但响应丢失时不切换到其它网关。
- 结果按 `record_id`/`ingest_key` 幂等处理；只有历史成功处理后才推进本地游标。
- 上游进入终态后仍需拉取到 `has_more=false`，再完成内部 Run。
- Worker 中断后，恢复接口重新让未完成 Run 进入可唤醒状态；重复结果由历史幂等保证不重复产生快照和事件。

### 历史边界

- `ingest_key` 只用于投递去重。
- `subject` 由 `ContentPolicy` 生成，用于跨 Run 找到同一个 Document。
- `upstream_external_id` 只用于追溯。
- `ContentPolicy` 生成规范化版本材料和内容指纹，并决定无变化、修订、缺失怀疑、缺失确认和恢复。
- 快照和变化事件由 `ContentHistory` 产生；适配器不能直接提交变化事件。

### 参考实现

- 核心不依赖 Web 框架、ORM、队列或供应商 SDK。
- 提供线程安全的内存运行状态和历史存储，用于测试和 CLI 独立演示。
- 提供基于 Python 标准库 HTTP 客户端的统一采集 API 网关，协议差异只留在该适配器。
- 提供可组合的网关回退路由；它实现 `UpstreamJobGateway`，不会进入领域契约。

## 泄漏与分层审计

- 存储行、HTTP 请求/响应、供应商 DTO、状态码和 SDK 异常不会进入核心契约。
- 上游游标只存在于内部 Run 状态；公共查询游标与上游游标相互独立。
- `CollectionAdapter` 同时拥有场景请求验证、上游任务构造和结果映射，避免调用方协调三个浅层处理器。
- `ContentPolicy` 拥有内容身份、规范化和比较规则；更换上游提供方不会改变历史身份。
- 不建立全局 `utils`、`services`、`repositories` 或 `common` 目录。
- 运行时不拆出只转发 `submit/observe/read` 的浅层服务；上游网关是协议端口，采集引擎是运行协调者。
- 回退、重试、游标推进、事务写入顺序和失败分类集中在采集引擎及网关适配边界内。

## 实现计划

1. 实现稳定契约和公共错误。
2. 实现扩展注册、采集端口、历史端口和内存适配器。
3. 实现 `ContentHistory` 和不可变快照/变化事件。
4. 实现 `CollectionEngine`、Run 状态、Attempt、重试、回退、恢复和结果核对。
5. 实现统一采集 API 网关和 CLI 演示适配器。
6. 编写契约、历史、幂等、范围隔离、至少一次投递、恢复、网关协议和 CLI 测试。
7. 运行格式/导入边界检查和完整测试，补齐公共文档。

## 未来变化的局部化结果

- 新采集场景：增加适配器和内容策略，不修改核心 Run/历史状态机。
- 新上游提供方：增加 `UpstreamJobGateway` 实现或路由候选，不修改业务调用方。
- 新数据库或对象存储：实现对应端口，不修改契约和内容策略。
- 新宿主平台：在应用装配层映射 `scope_key`、`actor_ref` 和执行限制，不把平台模型搬进核心。
- 只有在真实需求出现独立发布、重型依赖或团队边界后，才拆成多个发布包。
