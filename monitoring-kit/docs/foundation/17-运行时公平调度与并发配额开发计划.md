# monitoring-kit 运行时公平调度与并发配额开发计划

对应 GitHub Issue：[#5 增加按 scope / gateway 的公平调度与并发配额](https://github.com/yachenyanyi/reusable-packages/issues/5)。

## 1. 定位与当前状态

该能力属于可复用运行时扩展。首轮实现已经在当前工作树落地为可选能力，但它不是平台套餐系统，也不是必须部署的独立调度服务。只有出现共享部署、多 Worker 和真实 noisy-neighbor 压力时，才继续增加更复杂的调度策略。

没有 `RuntimePolicy` 时仍使用简单默认路径；已有 FIFO/lease 使用同一租约和状态版本围栏，不要求额外服务。

## 2. 要解决的问题

- 单个高流量 scope 长期占满全部 Worker，低流量 scope 饥饿。
- 单个 gateway 被并发任务打满，同时阻塞其它可用 gateway。
- 多进程 Worker 各自使用本地 semaphore，合计并发超过限制。
- Worker 崩溃后，租约占用不能及时恢复。

这里处理的是运行约束，不解释额度来自免费版、企业版还是客户合同。

## 3. 复杂度目标

- `CollectionEngine` 只推进已领取的 Run，不逐步实现公平算法和配额计数。
- Worker 只请求“一批可执行工作”，不遍历 scope、计算占用或协调其它 Worker。
- 平台只提供已经计算好的通用运行策略，不把套餐和用户模型传入核心。
- 公平算法、共享占用、租约恢复和数据库方言隐藏在一个深调度模块内。
- 没有策略配置时保持当前简单、低成本的运行方式。

## 4. 方案比较

### 方案 A：不断扩展 claim_runnable 参数

在现有方法上增加 scope limit、gateway limit、priority、weight、rate 等参数。

这会让 RunStateStore 同时暴露数据库领取和调度策略，调用方还要准备复杂映射。随着策略增加，方法会变成布尔开关和字典集合，且公平算法容易复制到不同适配器。

### 方案 B：引入 WorkAllocator 深模块

由 `WorkAllocator` 拥有公平选择、共享配额、租约和恢复语义；Worker 只调用一次分配操作。关系型与内存实现通过同一契约测试，数据库方言只负责原子领取。

选择方案 B。当前第一版已支持 per-scope、公平轮转、全局和 gateway 并发上限；权重、速率限制、熔断和背压不与第一版捆绑。

## 5. 候选接口

面向 Worker 的最小接口：

```text
WorkAllocator.allocate(AllocationRequest) → AllocationBatch
```

`AllocationRequest` 只包含 Worker 身份、批量上限、当前时间和租约时长等运行时拥有的信息。返回值是已带有效租约的 Run，不暴露 SQL 锁或内部配额账本。

平台接入侧可以提供通用策略：

```text
RuntimePolicy
  max_concurrent_runs
  scheduling_priority
  fairness_weight          # 后续真实需要时再启用
  gateway_limits           # 第二阶段
```

策略需要版本化并进入共享运行时状态，不能仅保存在某个 Worker 内存中。固定本地运行不配置策略时，使用默认无限制策略。

如果 `gateway_limits` 非空，排队 Run 必须在 `UpstreamJobRequest.gateway_hint` 中携带可确定的 gateway。因为 Run 在分配时还没有上游 Job，无法等到 `submit` 返回实际 gateway 后再补做配额判断；缺少 hint 时提交应返回配置错误，而不是把该 Run 归入一个未受限的未知 gateway。

`CollectionEngine.wake()` 是运行推进入口，内部唯一通过 `WorkAllocator.allocate()` 领取工作；旧的 `claim_runnable(...)` 仅兼容转发到同一分配语义，不能形成第二套调度路径。

## 6. 公平与配额语义

第一版采用可证明、容易测试的规则：

- 全局批次上限限制一次分配数量，不等同于全局并发配额。
- per-scope 并发按未过期运行租约计算。
- 在多个有资格的 scope 间使用持久化轮转，避免每次从固定最小 scope 开始。
- 同一 scope 内保持可解释的稳定顺序，例如 `next_wakeup_at + accepted_at + run_id`。
- 租约过期后自动释放占用；旧 Worker 仍受现有 state_version fencing 保护。
- priority 只能影响选择顺序，不能让低优先级 scope 永久饥饿。

第一版不实现加权公平。只有普通轮转无法满足真实吞吐目标时，再评估 deficit round robin 等算法。

## 7. 分阶段实施与后续验收

### 阶段 0：采集证据与建立基线

- 构造至少三个 scope、两个 gateway、多 Worker 的压力场景。
- 记录等待时间、领取分布、并发峰值和 lease 恢复时间。
- 明确可接受的最大等待时间和并发误差。
- 如果现有 FIFO 没有出现饥饿或上游压力，本计划保持待办，不进入生产实现。

### 阶段 1：接口设计与简单公平

- 定义 `AllocationRequest`、`AllocationBatch` 和最小 `RuntimePolicy`。
- 把 Run 领取从 CollectionEngine 的执行推进中分离，但避免只做转发的 Scheduler 包装。
- 实现无策略时的兼容路径。
- memory 实现固定轮转、公平和 lease 语义。

### 阶段 2：共享 per-scope 配额

- 在关系型存储中保存策略版本和公平游标，或使用能证明原子性的等价状态。
- 在同一领取事务中检查有效租约数量并预留容量。
- SQLite 采用适合单写者的事务方案；MySQL 使用行锁/跳锁等私有方言能力。
- 多 Worker 并发领取不能超过 scope 上限。

### 阶段 3：gateway 并发限制

- 先确保 Run 在排队阶段已有稳定的 resolved gateway key；不能依赖尚未执行的路由结果。
- gateway 达到上限时，其它 gateway 的 Run 仍可被领取。
- 只有真实需求证明必要时，才增加 source 级限制。
- 候选查询不能只取批次大小的前几条；前面的候选 gateway 饱和时，仍要继续检查同一 scope 后面的可用候选。

### 阶段 4：故障恢复与可观测性

- Worker 崩溃、数据库暂时不可用和 lease 到期后，容量能够恢复。
- 输出按 scope/gateway 聚合的等待与占用指标，不输出敏感 scope 原文到不受控日志。
- 检测长期饥饿并形成诊断事件，但不在本轮自动修改策略。

### 阶段 5：真实 MySQL 压力验收

- 多进程并发领取持续运行，验证上限无超卖。
- 高流量 scope 存在时，低流量 scope 在约定时间内获得执行机会。
- 一个 gateway 饱和时，其它 gateway 保持推进。
- 随机终止 Worker 后，过期租约被回收，旧 Worker 无法覆盖新状态。

## 8. 契约测试

- 默认策略与当前 FIFO 行为兼容。
- 两个 scope 使用相同配额时不会长期饥饿。
- 单个 scope 在多个 Worker 下不超过并发上限。
- 租约续期、过期和重新领取正确反映占用。
- priority 不破坏最低公平保证。
- gateway 配额只限制对应 gateway。
- 策略版本变化不会让旧 Worker 绕过新限制。
- gateway 配额配置缺少可确定的 `gateway_hint` 时，提交阶段稳定失败。

## 9. 非目标

- 不实现套餐、余额、计费、VIP 或客户等级。
- 不实现通用 cron 调度、工作流编排或队列产品。
- 不在第一版加入速率限制、熔断、背压和自动扩缩容。
- 不承诺严格实时或数学意义上的完美公平。
- 不让单进程 semaphore 成为跨进程正确性保证。

## 10. 完成标准

- 分配入口唯一，Worker 不再自行协调 scope 和 gateway 配额。
- 多 Worker 下的上限由共享状态原子保证。
- 默认独立运行模式无需平台、策略表或额外服务即可工作。
- 公平性和容量恢复都有可重复的压力测试证据。
- 平台业务只映射为通用 RuntimePolicy，不进入核心模型。
- CollectionEngine 不因增加新调度策略而继续膨胀。
