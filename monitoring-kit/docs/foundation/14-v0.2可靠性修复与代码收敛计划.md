# monitoring-kit v0.2 可靠性修复与代码收敛计划

对应 GitHub Issue：[#1 RunStateStore 多 Worker 并发保护](https://github.com/yachenyanyi/reusable-packages/issues/1)、[#2 ContentHistory 多 Worker 并发一致性](https://github.com/yachenyanyi/reusable-packages/issues/2)。

## 1. 任务

修复关系型持久化适配层和统一采集边界中已经确认的可靠性问题，使 SQLite 单机运行、MySQL 8+ 多 Worker 运行和内容历史并发写入具备清楚且可验证的正确性。

本轮不是重写核心，也不扩展站点、GEO、舆情等业务能力。修复必须继续保持：核心只依赖领域端口，SQLAlchemy、数据库锁、DDL 和驱动差异全部留在适配器内部。

修复前基线为 `42 passed`。自动化测试尚未覆盖真实 MySQL、租约过期后的旧 Worker 写入、同一 Document 的跨实例并发提交和并发 schema 初始化。

## 2. 复杂度目标

- 让并发冲突成为两个明确的内部概念，而不是散落在 SQL、异常文本和重试分支中。
- 让数据库字段能够真实承载现有领域契约，不依赖 SQLite 对字段长度的宽松行为。
- 让调用方继续只负责装配和关闭 bundle，不负责选择方言、组织事务或修复并发竞态。
- 把查询限制、安全脱敏和损坏数据分类压入拥有这些知识的边界模块。
- 修复后减少代码中的重复异常处理和无用导入，但不借机重构无关模块。

## 3. 防止形成“史山”的硬约束

本轮实现必须遵守以下限制：

- 不新增通用 `Repository`、`BaseStore`、`Manager`、`Service` 或全局 `utils`。
- 不为 SQLite/MySQL 各复制一套 Store；共同语义仍只有一个实现。
- 不增加 `backend=mysql/sqlite` 参数，数据库类型仍只由 `database_url` 决定。
- 不把 SQLAlchemy 行、Connection、事务、版本号或锁对象暴露为公共 API。
- 不用布尔开关拼接不同并发语义；冲突通过有名称的内部错误表达。
- 不为尚未出现的第三种数据库设计公开方言 SPI。
- 不同时引入 Alembic、队列、Outbox 和对象存储；它们分别按真实需求演进。
- 每个生产代码改动必须对应一个失败测试或明确的不变量，测试先复现、再修复。

预计修复主要留在现有文件中。只有当一个概念需要被核心和多个适配器共同识别时，才允许在相应核心端口旁增加一个小型内部类型或错误。

## 4. 已确认问题

### 4.1 Run 请求指纹与 MySQL 字段不匹配

`RunRequest.fingerprint()` 当前返回完整规范 JSON，但数据库列是 `VARCHAR(128)`。现有测试请求的指纹已达到 193 字符；MySQL 严格模式会拒绝写入，非严格模式可能截断并破坏幂等判断。

同时，`record_json`、`result_json`、`snapshot_json` 等字段使用 MySQL `TEXT`，其约 64KB 上限不足以稳定承载网页正文、模型回答和完整历史结果。

### 4.2 Run 租约缺少过期 Worker 的写入围栏

`claim_runnable` 能避免有效租约期间的重复领取，但 `save(record)` 只按 `run_id` 更新。旧 Worker 的租约过期后，新 Worker 即使已经重新领取，旧 Worker 仍能覆盖状态、游标和新租约。

### 4.3 History 提交可以覆盖更新后的 Document

`ContentHistory` 在事务外读取和计算结果，`HistoryStore.commit` 在事务内只检查新 Snapshot revision 和 ChangeEvent sequence。一个基于旧 Document 计算出的“无变化”结果没有新 Snapshot 或事件，因此可能在另一个写入完成后把 `current_snapshot_id`、`missing_streak` 或观察时间写回旧值。

### 4.4 schema 初始化存在并发竞态

`has_table` 与 `create_all(checkfirst=True)` 不是一个原子操作。多个进程同时启动时，可能同时判断表不存在，随后部分进程因 `table already exists` 失败；schema version 首次插入也存在同类竞态。

### 4.5 变化查询没有把限制下推到数据库

`query_changes` 会把游标后的全部 scope 事件读取到内存，再执行过滤和 `limit`。长期运行后，一次小分页查询也可能扫描并构造大量 Python 对象。

### 4.6 边界校验和错误分类不完整

- `safe_url` 只隐藏 URL 用户信息中的密码，查询参数中的密码或 Token 仍可能被返回。
- 损坏的 Document 载荷可能从 `get_document` 泄漏原始 `KeyError` 或 `ValueError`。
- 上游结果的 `deleted` 没有统一校验为布尔值，字符串 `"false"` 可能被当作真值并产生错误的缺失观察。

### 4.7 公平分配与首次建档的并发边界

本轮实现复核后补充以下必须收口的边界，它们仍属于 Issue #1/#2 的关系型可靠性范围：

- MySQL 严格 `ONLY_FULL_GROUP_BY` 下，按 scope 统计必须同时按投影字段分组；不能依赖 SQLite 的宽松行为。
- 分配器的共享公平游标必须用普通 `FOR UPDATE` 等待竞争者；不能用 `SKIP LOCKED` 跳过唯一状态行。
- 必须在锁定公平游标后再读取 active 计数，并且不能因为一个 scope 前面的 gateway 已饱和而截断候选集。
- 两个 Worker 同时创建不存在的 Document 时，唯一键竞争应转换成 `HistoryWriteConflictError` 并由 `ContentHistory` 有限重算；只有找不到竞争 Document 时才归类为持久化不变量错误。

## 5. 方案比较与选择

### 5.1 请求指纹

方案 A：把数据库列改成无限增长的文本，继续保存完整规范 JSON。

方案 B：规范 JSON 只作为哈希输入，`fingerprint()` 返回固定长度 SHA-256；完整 `RunRequest` 仍由 Run 载荷保存。

选择方案 B。幂等判断只需要稳定相等性，不需要从指纹反解请求。固定摘要减少数据库耦合和索引风险，也让“fingerprint”名称与实际语义一致。摘要算法和编码方式必须写入契约测试，不能依赖 Python 对象哈希。

### 5.2 Run 并发控制

方案 A：让 `save` 根据 `record.lease_owner` 拼接条件更新。

这个方案无法干净处理释放租约、取消请求和恢复流程；调用方清空 `lease_owner` 后会丢失用于证明所有权的信息，同一 worker ID 复用也不能形成可靠围栏。

方案 B：为 Run 内部状态增加单调递增的 `state_version`，所有保存使用 compare-and-swap；领取任务也增加版本。版本不进入公共 `RunSummary`，数据库适配器只在 `WHERE run_id AND state_version` 中使用它。

选择方案 B。它同时解决租约过期、取消与 Worker 推进之间的覆盖，不需要增加公开 lease token。冲突使用一个位于 `collection` 端口边界旁的内部错误表达，旧 Worker 遇到冲突后放弃本地状态，不能把 Run 标记为失败。

### 5.3 History 并发控制

方案 A：把数据库版本 token 加入公共 `Document`，由核心一路传递到 Store。

这会让持久化机制进入稳定契约，并形成只为透传而存在的变量。

方案 B：`HistoryWrite` 携带本次结果所依据的旧 `Document`；Store 在事务内锁定当前 Document 后比较。不存在、内容不同或已经被更新都视为内部写入冲突，`ContentHistory` 重新读取并重新计算。

选择方案 B。`HistoryWrite` 本来就是历史模块的内部事务命令，携带计算依据属于它的真实语义，不需要给公共 `Document` 增加数据库字段。重试次数保持一个小的固定上限，超过后返回稳定基础设施错误，不能无限自旋。

### 5.4 schema 初始化

方案 A：要求所有宿主在启动 Worker 前单独运行初始化命令。

方案 B：保留 `open_persistence` 的便利初始化，在私有方言层提供初始化临界区：SQLite 使用数据库写锁，MySQL 使用数据库级 advisory lock；锁内重新检查、建表并写入版本。

选择方案 B，保留独立运行的简单体验。初始化锁只是关系型适配器的私有知识，不增加公共 SPI。未来真正引入迁移工具时，可以替换 `schema.py` 的实现而不改变核心和装配 API。

### 5.5 MySQL 大字段和运行假设

JSON 载荷列在 MySQL 使用 `LONGTEXT` 方言变体，SQLite 继续使用共享文本类型。新建 MySQL 表明确使用 InnoDB 和 `utf8mb4`。这些差异只出现在 `schema.py`，不创建 MySQL 专属 Store。

本轮不实现把正文自动搬入对象存储。是否把超大内容替换为 `artifact_ref` 是独立的存储策略，必须等真实内容规模和访问模式明确后再设计。

### 5.6 变化查询

过滤条件、`event_order > cursor` 和 `limit + 1` 全部下推到 SQL；多取的一行只用于判断 `has_more`。先复用现有索引，不因为可能出现的查询组合提前创建大量复合索引。真实慢查询出现后再依据执行计划增加索引。

## 6. 模块职责与接口变化

### `contracts/run.py`

- 将请求指纹定义为稳定 SHA-256 摘要。
- 不增加数据库或方言概念。
- `RunRequest` 的公共字段和调用方式保持不变。

### `collection/model.py` 与 `collection/ports.py`

- `RunRecord` 增加包内运行状态版本，不进入公共摘要。
- 定义 Store 实现和 `CollectionEngine` 共同理解的并发冲突。
- `save(record)` 的方法形状尽量保持不变，由 Store 在成功保存后推进记录版本。
- `CollectionEngine` 遇到版本冲突时放弃当前副本，不执行失败状态覆盖。

### `history/model.py` 与 `history/history.py`

- `HistoryWrite` 明确携带计算所依据的旧 Document。
- `ContentHistory` 只对明确的并发冲突重新读取和重新计算；其它数据库错误不伪装成冲突。
- 重试逻辑留在 `ContentHistory.record` 内部，调用方仍只调用一次 `record(observation)`。

### `adapters/persistence/relational/`

- `run_state_store.py` 实现 Run 版本 CAS。
- `history_store.py` 在锁内验证 HistoryWrite 的计算依据，并完成 SQL 分页下推。
- `schema.py` 统一拥有字段容量、MySQL 表选项、schema version 和并发初始化。
- `codecs.py` 统一把损坏载荷转换为稳定的持久化不变量错误。
- `bundle.py` 只负责配置、装配、生命周期和安全诊断 URL，不吸收 Store 逻辑。
- `dialects/` 只保留事务、行锁和 schema 初始化锁等真实数据库差异。

### 统一采集结果边界

`UpstreamRecord` 统一验证 `deleted` 为布尔值，使所有网关实现得到同一约束。HTTP 适配器继续负责把该校验错误翻译成 `UPSTREAM_PROTOCOL_ERROR`。

## 7. 分阶段实施与验证

### 阶段 1：先固定失败测试

只增加最小复现测试，不改生产代码：

- 大于 128 字符的 RunRequest 能在关系型 Store 中往返。
- 旧 Worker 在租约过期并被重新领取后不能保存。
- 同一 Document 的“新版本”和基于旧状态的“无变化”并发提交不能使当前指针回退。
- 多个连接同时初始化同一个 SQLite 文件数据库，所有调用最终成功并看到同一 schema version。
- 带过滤条件的变化分页只返回 `limit`，游标不遗漏、不重复。
- `safe_url` 不返回查询参数中的敏感值。
- 损坏数据库载荷只产生稳定持久化错误。
- `deleted="false"` 被当作协议错误，而不是删除事实。

阶段门槛：这些测试必须先按预期失败，并准确指向已确认问题，不能用大范围 mock 代替真实 SQLite 并发。

### 阶段 2：修复数据表示

- 把请求指纹收敛为固定摘要。
- 为 MySQL JSON 载荷使用 `LONGTEXT` 方言变体。
- 明确新建 MySQL 表的 InnoDB 与 `utf8mb4`。
- 明确 `mysql+pymysql://` 为默认支持的 MySQL URL；缺少驱动时返回配置错误，而不是模糊的不可用错误。

schema 版本策略：当前关系型 schema 尚未正式发布且测试数据库均为临时实例时，可以直接修正初始 schema 定义；一旦存在需要保留的真实数据库，就必须提升 `SCHEMA_VERSION` 并提供显式前向迁移，不能在同一版本号下静默改变字段。

### 阶段 3：修复并发不变量

- 先实现 Run 状态版本和 CAS，再调整引擎冲突处理。
- 再实现 HistoryWrite 计算依据校验和有限重算。
- 最后实现 schema 初始化临界区。
- 为首次 Document 建档的唯一键竞争增加 savepoint 和冲突重读；为公平分配增加共享状态锁、严格分组和完整候选扫描。

阶段门槛：所有并发测试至少重复运行多轮；测试结果必须检查最终数据库事实，而不只检查是否抛异常。

### 阶段 4：收敛查询、安全和错误

- 将变化查询过滤和限制下推到 SQL。
- `safe_url` 解析失败时返回固定占位文本，绝不回显原始连接串；诊断 URL 默认移除全部 query。
- 统一数据库载荷解码错误，不允许 `KeyError`、JSON 异常或数据库行泄漏到核心。
- 在 `UpstreamRecord` 统一校验布尔字段。

### 阶段 5：真实 MySQL 验收

使用 MySQL 8+、InnoDB、`utf8mb4` 运行高价值契约测试：

- Run 创建、读取、保存和幂等提交。
- 两个独立连接并发领取。
- 旧 Worker 写入围栏。
- History 原子回滚、重复 ingest 和 Document 并发冲突。
- 超过 64KB 的 JSON 载荷往返。
- 并发 schema 初始化。

MySQL 测试通过可选环境变量启用，普通本地测试没有 MySQL 时可以明确跳过；CI 或发布前验收必须至少有一个真实 MySQL 任务。不要把全部 HTTP 场景乘以数据库矩阵。

### 阶段 6：代码卫生收尾

- 删除本轮产生或确认的无用导入。
- 把 `open_persistence` 中重复的 engine 清理逻辑收敛为一个私有分支。
- 只在已有重复已经表达同一稳定概念时提取私有帮助函数。
- 同步更新关系型适配层文档、测试说明和 schema version 说明。
- 不移动无关文件，不重命名稳定公共接口，不做全仓格式化。

## 8. 完成标准

- SQLite 单机和 MySQL 多 Worker 的关键语义都有真实数据库测试。
- 旧 Worker、旧 History 计算结果和并发初始化都不能覆盖较新事实。
- 请求指纹长度固定，MySQL 大字段能够承载约定范围内的监测载荷。
- `query_changes` 的数据库读取量受 `limit + 1` 约束。
- 数据库错误、损坏载荷和敏感连接信息不会越过适配边界。
- 核心仍不导入 SQLAlchemy、方言或数据库异常。
- 公开装配 API 仍只有 `PersistenceConfig`、`open_persistence` 和 `PersistenceBundle`。
- 不出现新增的通用 Repository、Manager、Service、全局工具箱或数据库专属核心分支。
- 现有测试和新增回归测试全部通过，`compileall`、导入边界检查和 `git diff --check` 通过。

## 9. 明确后置事项

以下问题不混入本轮修复：

- Outbox 与消息队列可靠投递。
- 大对象自动迁移到 ArtifactStore。
- Alembic 或其它完整迁移框架。
- PostgreSQL 和第三种关系型数据库。
- 业务套餐、用户任务、站点、GEO、舆情专属表。
- 通用插件系统、动态发现和热加载。

这些能力以后可以接入现有端口，但不能成为本轮并发正确性修复的前置条件。
