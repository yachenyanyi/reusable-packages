# 架构决策

这里只记录会影响多个模块或多个项目的稳定决策。单一客户的技术约束写入对应项目档案。

## ADR-001：模块化单体优先

选择：领域边界独立，默认同应用部署；满足独立扩缩容、故障隔离、团队所有权或合规要求后再拆服务。

拒绝：一开始为每个模块建设微服务。原因是网络、部署和一致性复杂度高于当前收益。

## ADR-002：稳定外壳与有类型载荷

选择：Observation 使用统一身份、来源、时间、证据和版本字段；网页、模型回答和帖子使用有类型的业务载荷。

拒绝：所有字段放进无结构 JSON，或强迫所有来源使用一张巨大的稀疏模型。

## ADR-003：原始证据与不可变快照

选择：保留原始证据引用；Snapshot 不覆盖，Document 指向当前版本。

收益：可以重新解析、重新分析、审计历史结论。

## ADR-004：来源差异收敛到适配器

选择：供应商字段、分页、选择器和外部异常由 SourceAdapter 转换。

拒绝：在采集引擎中不断增加来源类型判断。

## ADR-005：运行时隐藏重试与回退

选择：调用方表达采集意图；Acquisition Runtime 内部处理 HTTP、浏览器、API、模型调用、退避和回退。

拒绝：让业务层传递 use_browser、retry_count、queue_name 等实现参数。

## ADR-006：配置分层且运行时冻结

选择：TaskDefinition、SourceProfile、RuntimePolicy 和 Secrets 分离；Run 启动时保存实际版本。

收益：配置可变，但历史运行可解释、可复现。

## ADR-007：调度和队列是可替换基础设施

选择：小规模可使用轻量调度；规模增长后可切换队列和多 Worker，领域接口不变。

拒绝：让 APScheduler、Celery 或其它框架类型进入 Task/Run 模型。

## ADR-008：AI 只产出可解释发现

选择：确定性规则先筛选，AI 结果记录证据和版本，最终进入人工可确认的 Finding。

拒绝：让 AI 直接执行删除、整改或公开通知。

## ADR-009：任务型统一采集 API 为主接入模式

选择：监测系统提交采集任务并保存稳定的上游任务 ID；状态查询与结果接口是事实来源，事件流用于及时反馈，游标用于部分结果和断点续传。

约束：提交必须幂等；结果记录必须有稳定 ID 和 schema 版本；终态后必须可以拉取并核对完整结果。

拒绝：仅依赖 Webhook 或事件流判断完成，也不把上游任务 ID 直接用作内部 Run ID。

兼容：没有统一 API 的独立部署可以提供直接采集适配器，但不改变采集引擎和内容历史的领域接口。
