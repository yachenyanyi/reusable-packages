# 运行与部署形态

架构先定义稳定职责，部署形态按规模演进。模块不等于进程，更不等于微服务。

## 形态 A：开发与小规模交付

```text
Web/API 进程
Worker 进程
关系数据库
本地或对象文件存储
进程内或轻量调度器
```

适用于百级来源、低频运行和单团队维护。重点是保证 Run 状态、幂等、证据和审计，而不是先建设分布式基础设施。

## 形态 B：多 Worker 运行

```text
API
Scheduler
Queue
Collection Workers
Analysis Workers
关系数据库
对象存储
```

当出现队列积压、任务耗时差异、需要独立扩缩采集和分析能力时采用。可以引入 Redis/Celery 等实现，但领域接口保持不变。

## 形态 C：选择性服务化

只有满足以下条件之一才拆服务：

- 模块需要独立扩缩容或资源隔离。
- 故障必须与主应用隔离。
- 不同团队拥有独立发布节奏。
- 数据或供应商存在明确合规边界。

即使拆服务，也优先沿既有深模块边界拆，不按数据库表或技术步骤拆。

## 存储建议

- 关系数据库：Task、Run、状态、索引、版本元数据、Finding、Case 和审计。
- 对象存储：原始 HTML、JSON、截图、模型回答、附件和报告文件。
- 搜索引擎：只有关系数据库检索已成为真实瓶颈时再引入。
- 缓存：只优化性能，不作为业务事实唯一来源。

## 运行保障

- 每个 Run、Item、Attempt 都有稳定关联 ID。
- Worker 重启后不会重复产生业务结果。
- 重试具有退避和抖动，来源级限速独立。
- 配置、适配器、分析方案和模板均记录版本。
- 凭证通过 secret_ref 获取，不进入任务配置和日志。
