# 扩展类型信封（TypedEnvelope）

## 目的

让模块可以增加新的采集规格、内容类型和变化详情，同时保留运行前验证、版本兼容和历史回放能力。

## 结构

```text
TypedEnvelope {
  type_key
  schema_version
  data
}
```

- `type_key` 使用稳定、带命名空间的标识，例如 `org.example.geo.answer`，不能使用容易重名的 `answer`。
- `schema_version` 描述 data 的语义版本，不等于代码包版本。
- `data` 的结构必须由该类型发布的 schema 定义，不能是无约束键值袋。

## 处理器注册

```text
TypeHandler {
  type_key
  supported_versions
  validate(data, version)
  decode(data, version)
}
```

不同使用位置在基础处理器之外增加自己的能力：

- `CollectionAdapter`：验证 Run 规格、构造上游任务请求，并把该任务的版本化上游记录映射成内部 `ObservedRecordDraft`。
- `ContentPolicy`：生成持续对象身份、规范化内容、决定是否形成新 Snapshot，并解释差异。

采集请求和对应结果的知识放在同一个深适配器中，避免调用方协调两个必须配对的浅模块。`ContentPolicy` 单独存在，因为它由内容类型决定，并且会独立于上游供应商变化。

## 插拔规则

- 所有处理器在 composition root 启动时显式注册。
- 同一 `type_key + 主版本` 不能同时注册两个所有者。
- 缺失处理器时启动检查应尽早报错；遇到历史未知类型时数据必须保留并进入不可处理状态，不能静默丢弃。
- 移除扩展前必须确认历史数据仍有旧处理器或迁移方案。
- 第一版不支持从网络下载扩展、不可信代码执行和运行时热替换。

## 为什么这不等于“随便放 JSON”

存储层可以把 data 保存为 JSON，但契约层仍要求命名类型、明确 schema、验证器、兼容策略和测试。JSON 只是编码方式，不是领域设计。

## 契约测试

每个扩展至少验证：

- 合法载荷可以稳定往返序列化。
- 非法字段、缺失字段和未知版本被明确拒绝。
- 同一内容经过规范化得到稳定结果。
- 旧版本能由旧处理器读取，或有确定升级路径。
- 不认识可选的新字段时，同一主版本的读取方仍能工作。
