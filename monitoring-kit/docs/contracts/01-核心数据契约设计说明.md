# 核心数据契约设计说明

## 任务

设计能同时支持站点、GEO、舆情和未来监测场景的 `RunRequest`、`Observation`、`ChangeEvent`，并允许代码库独立运行或嵌入现有平台。

## 复杂度目标

- 新增场景时不修改核心契约的固定字段。
- 替换统一采集 API 时不影响业务模块。
- 核心仍能在运行前验证扩展数据，不接受无法解释的自由 JSON。
- 契约升级、历史回放和数据迁移具有明确版本边界。

## 候选方案

### 方案 A：超级统一模型

把 URL、正文、模型、提示词、作者、互动量、引用等全部放在同一模型。查询直观，但每增加场景都要修改核心，字段大多为空，场景语义互相污染。

### 方案 B：核心只保留任意 JSON

扩展最快，但验证、版本、比较和错误处理全部落到运行期；调用方无法知道某个 payload 是否真的可处理。

### 方案 C：稳定信封加注册式类型契约

核心拥有身份、时间、幂等、追溯和生命周期字段；场景数据放在带 `type_key` 与 `schema_version` 的扩展信封中，并由装配时注册的处理器验证和解释。

选择方案 C。它比方案 A 更容易扩展，比方案 B 更可验证。代价是每个扩展必须维护自己的 schema、升级器和测试，这是合理的模块责任。

## 模块和接口

```text
宿主 ──RunRequest──→ Collection Engine
                         │
                 CollectionAdapter（扩展 SPI）
                         │
统一采集 API ───────────原始记录
                         │
                  ObservedRecordDraft（内部）
                         │
                  ContentPolicy（扩展 SPI）
                         ↓
                    Observation
                         ↓
             Content History + ContentPolicy
                         │
                    ChangeEvent
```

`CollectionAdapter` 同时拥有某一采集类型的规格验证、上游请求转换和结果映射，避免宿主协调一串浅层处理器。`ContentPolicy` 拥有某种内容的持续对象身份、规范化和版本比较规则，因此更换上游供应商不改变历史语义。核心使用注册表按 `type_key + schema_version` 找到扩展，但注册、装配和生命周期由宿主负责。第一版不做运行时下载、热加载和插件沙箱。

## 隐藏的实现知识

- 上游任务字段、供应商 DTO、分页和错误码。
- 场景 payload 的验证与版本迁移。
- 哪些字段属于内容修订、哪些只是易变指标。
- 哈希、快照推进、缺失确认和恢复判断。
- 数据库、对象存储和事件中间件格式。

## 泄漏风险

- 把 `cursor`、`upstream_job_id` 或重试参数放进 `RunRequest`。
- 把网站、GEO、舆情字段直接加入 `Observation` 固定部分。
- 允许调用者提交 `ChangeEvent`，绕过内容历史不变量。
- 把 ORM 实体或供应商异常作为契约输入输出。
- 用一个无 schema 的 `metadata` 袋子承载所有未来需求。

## 测试与兼容性

- 每个核心契约提供序列化、反序列化和不变量测试。
- 每个扩展处理器通过统一契约测试套件。
- 保存历史 payload 时同时保存 `type_key` 和 `schema_version`。
- 同一主版本只能兼容增加；改变字段语义必须升主版本并提供升级器或保留旧处理器。
