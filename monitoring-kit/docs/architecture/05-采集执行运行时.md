# 采集执行运行时（Acquisition Runtime / Upstream Job Gateway）

## 目的

以任务型统一采集 API 为主路径，可靠提交、跟踪和获取上游结果；对上层隐藏幂等提交、事件、游标和供应商协议差异。轮询、重试和回退的运行协调由 `CollectionEngine` 持有，网关只翻译外部协议。

## 公开能力

```text
submit(UpstreamJobRequest, idempotency_key) → UpstreamJobRef
get_status(upstream_job_ref)                → UpstreamStatus
read_batch(upstream_job_ref, cursor)        → UpstreamBatch
cancel(upstream_job_ref)                    → UpstreamCancellation
```

这些是采集引擎内部端口。统一 API 的 HTTP 路径、状态码、Webhook 和供应商 DTO 不得越过该边界。

## 主路径：统一采集 API

- 使用内部 `run_id` 作为幂等提交依据，保存 `upstream_job_id`。
- 以状态查询和结果接口作为事实来源。
- 事件/Webhook 用于及时唤醒，游标用于部分结果和断点续传。
- 上游终态后再次拉取并核对最终结果。
- 统一 API 的接入要求见 [统一采集 API 接入前提](../contracts/统一采集API接入前提.md)。

## 可选路径：直接采集适配器

如果某个独立部署没有统一 API，可以替换本模块的实现，使用 Web、API 或 Model 执行器直接采集。该能力不是当前主路径，不能让其技术参数泄漏到采集引擎接口。

## 内部职责

- 幂等提交、状态归一化、轮询退避和错误分类。
- Webhook/事件去重、乱序处理和轮询兜底。
- 游标检查点、部分结果恢复和最终结果核对。
- 上游结果与原始证据引用留存。
- 记录上游执行轨迹、用量和运行指标；运行状态和历史事实仍由核心端口保存。

## 不变量

- 同一内部 Run 重复提交不能创建多个上游任务。
- 结果成功持久化后才能推进本地 cursor。
- 事件丢失后可以通过状态和结果接口恢复。
- 上游任务进入终态后必须完成一次结果核对。
- 一次失败尝试必须可追溯，但业务层无需协调下一次尝试。

## 隐藏知识

统一 API 客户端、鉴权、HTTP 路径、状态映射、Webhook、游标、轮询、幂等和上游错误格式。

## 非目标

不定义用户业务任务、不比较内容版本、不判断内容风险、不把上游任务 ID 暴露成内部 Run ID。
