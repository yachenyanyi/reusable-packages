# 内容历史（Content History）

## 目的

把一次 `Observation` 变成可追溯的当前内容、历史版本和变化事件，隐藏幂等、身份索引、规范化、哈希和版本推进细节。

## 公开能力

```text
record(observation)                  → HistoryResult
get_current(document_id, scope_key)  → DocumentView
get_timeline(document_id, scope_key) → SnapshotTimeline
query_changes(query, scope_key)      → ChangePage
```

## 核心模型

- `Document`：外部对象的稳定身份和当前状态。
- `Snapshot`：不可变的某一内容版本。
- `ChangeEvent`：新增、更新、删除候选、确认删除、失联、恢复等事实。

## 处理规则

- 新外部标识产生 Document、首个 Snapshot 和新增事件。
- 规范化内容哈希变化时才创建新 Snapshot。
- 内容未变时只更新最后观察时间。
- 原始哈希与正文哈希分离，避免页脚和访问量造成误报。
- 未在列表页发现不能直接推断删除；404/410 与连续复查共同参与确认。
- 按 content 的 `type_key + schema_version` 调用已注册的 `ContentPolicy`，验证对象身份并生成修订判断；ABSENT 观察按 Subject 命名空间找到同一策略。

## 不变量

- Snapshot 不可覆盖修改。
- 每个 Snapshot 可追溯到 Source、Run、内部 Attempt 和原始证据。
- 同一 `ingest_key` 重复提交不会生成第二个 Snapshot 或 ChangeEvent。
- Document、Snapshot 和 ChangeEvent 必须与 Observation 处于同一 `scope_key`。
- 多 Worker 基于旧 Document 并发记录时，Store 必须拒绝过期计算结果；历史模块有限重读并重新比较，不能覆盖较新的 current 指针。
- 启用至少一次投递时，HistoryStore 与 ChangeEvent 同事务写入 Outbox；轻量直发路径不提供持久化投递保证。
- 解析规则变更后重新处理旧证据，不伪造新的采集时间。

## 隐藏知识

ContentPolicy 的选择、内容规范化、哈希算法、版本存储、当前版本指针、删除阈值，以及可靠投递模式下的 Outbox 写入意图和存储布局。

## 非目标

不负责外部采集、不判断业务风险、不决定发送什么通知。
