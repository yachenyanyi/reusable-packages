# 公共契约

## 契约原则

- 契约按 `type@major.minor` 标识版本；第一版使用 `website.discovery@1.0`、`website.collection@1.0` 和 `website.page@1.0`。
- 公共类型不包含 HTTP Response、Playwright Page、Crawlee Request、ORM 实体、数据库游标或供应商异常。
- 新增可选字段可以保持小版本兼容；改变字段语义、默认范围或身份规则必须升级主版本。
- 未知字段不能被解释为任意扩展行为。可扩展内容使用已注册、带版本的类型化载荷。

## 公共操作

```text
inspect_site(spec)  -> SiteInspection
collect_site(spec)  -> CollectionResult
refresh_pages(spec) -> CollectionResult
```

规格包含调用方真正拥有的站点范围和采集预算。幂等、租户作用域、API 鉴权和基础设施上限由宿主拥有，不作为本组件的透传参数；异步取消按最终语言的结构化并发方式定义。具体函数签名可以在语言选型后调整，但操作语义不得改变。

Python 内部的 `InspectionSpec` 和 `CollectionSpec` 不携带 `schema_version`；它们的字段版本由包版本管理。跨进程的 wire-level 版本由统一 API 的 DTO 负责，并在 DTO 与本组件规格之间显式转换。

## InspectionSpec

```text
inspection_id
site_ref
seeds
scope
budget
profile                optional
known_urls             optional
```

不变量：种子必须落在声明范围内；预算必须有上限；Profile 与 site_ref 必须一致。

## CollectionSpec

```text
collection_id
site_ref
intent                 site_sweep | targeted_refresh
seeds                  site_sweep 时使用
targets                targeted_refresh 时使用
scope
budget
profile                optional
known_urls             optional discovery hint
```

`known_urls` 只帮助发现和比较，不把长期历史所有权转移给本组件。调用方不传 `use_browser`、`retry_count` 或框架队列配置。

`url` 是该页面主候选实际使用的请求地址；`final_url` 是获取适配器返回的最终地址；`canonical_url` 只用于本次 Collection 的身份去重；`request_aliases` 保存映射到同一 canonical identity 的其它请求地址。`record_id` 在同一次 Collection 的重复读取中稳定；跨 Collection 的长期文档身份由上层系统生成。正文为空不一定是失败，例如附件或跳转页必须按页面类型解释。

## SiteInspection

```text
schema_type            website.discovery@1.0
inspection_id
site_ref
started_at / finished_at
candidates
route_families
page_type_samples
profile_draft
coverage

```

Profile 草案必须带推断依据和置信度，不能自动标记为已发布。

## CollectionResult

```text
schema_type            website.collection@1.0
collection_id
site_ref
status                 completed | partial | cancelled | failed
started_at / finished_at
pages
exclusions
issues
coverage
profile_ref
usage
```

大规模部署可以流式产生 `pages`，但最终摘要必须可核对。统一 API 如何分页和保存游标属于其传输契约，不改变本结果语义。

## Budget 与 Usage

`Budget` 的核心上限为 `max_pages`、`max_candidates`、`max_depth`、`max_duration_seconds`、`max_requests`、`max_total_bytes` 和可选的 `max_rendered_pages`。后几个资源上限分别约束所有获取尝试、所有已接收响应体和浏览器渲染页。

`Usage` 中的 `requests` 包含 robots、sitemap、RSS、页面、重定向和重试等所有 `AcquisitionPort.fetch` 调用；`bytes_received` 包含这些调用返回的所有响应体；`successful_pages` 和 `failed_pages` 只统计唯一页面，不统计 discovery issue。预算被拒绝的候选不会冒充失败页面。

## 错误契约

任务级、调用方可处理的错误：

```text
InvalidSpec
ProfileIncompatible
NoAcquisitionCapability
RequiredEvidenceUnavailable
```

网络超时、单页状态异常、解析失败、robots 禁止、内容类型不支持和越界重定向通常进入 `issues` 或 `exclusions`，不作为任务级异常抛出。

每个问题至少包含稳定 `code`、受影响 URL、阶段、是否可重试和可读说明；不得要求调用方解析异常文本。

## 副作用与幂等

- 同一 `collection_id` 的重复执行不得产生相互矛盾的多个逻辑结果；持久化幂等的具体实现由宿主与端口共同保证。
- 返回 `evidence_ref` 前，对应证据必须已经稳定保存或明确标注短期有效期。
- 取消和预算耗尽保留已经完成的页面结果。
- 任何访问都必须遵守 Scope；重定向后重新校验。
