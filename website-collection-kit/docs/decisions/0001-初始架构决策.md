# 初始架构决策

- 状态：Accepted，技术栈部分为 Proposed
- 日期：2026-09-03

## ADR-001：独立可复用组件

选择：将网站检查与采集放在 `packages/website-collection-kit/`，与 `monitoring-kit` 并列。

原因：它有独立用途、重型浏览器依赖和不同变化轴，也可被统一 API、CLI 或其它监测项目复用。

边界：两个组件不导入彼此私有模块。长期运行与历史仍由 `monitoring-kit` 负责。

## ADR-002：意图式深门面

选择：公共操作只表达检查、站点采集和定点复查。队列、抓取、解析、分类和覆盖评估作为内部协调。

拒绝：把每个执行步骤公开为服务。该方案会让调用方承担顺序、重试和中间状态，并制造浅模块。

## ADR-003：Profile 优先，代码策略受控

选择：普通网站差异由声明式、版本化 Site Profile 表达；复杂算法通过具名策略显式注册。

拒绝：每个网站一个模块，以及在 Profile 中执行任意脚本。

## ADR-004：获取技术是适配器

选择：HTTP、Playwright/CDP、爬取框架和证据存储通过端口接入，公共接口不暴露技术产品。

拒绝：让 Crawlee 或 Playwright 对象成为领域契约。

## ADR-005：静态优先、受控渲染回退

选择：在满足内容需要和 Profile 事实时使用渲染，回退由组件内部决定并设上限。

原因：大部分页面静态获取成本更低、证据更稳定；部分站点又必须执行 JavaScript。把选择权交给每个调用方会复制判断逻辑。

## ADR-006：覆盖是证据报告，不是绝对比例

选择：报告发现源、frontier 收敛、预算、路由族和已知盲区。

拒绝：在没有真实页面全集的情况下输出“已抓取 100%”。

## ADR-007：语言和框架延后到原型决策

候选一：Python，与 `monitoring-kit` 语言一致，使用内部异步编排、HTTPX、Playwright 及成熟正文提取库；Crawlee 作为可替换适配器候选。

候选二：TypeScript，利用 Crawlee/Playwright 更成熟的生态，通过统一 API 与 Python 系统隔离。

已验证 Python 与选定 Crawlee extras 可以运行，但 Crawlee 全量 extras 在 Python 3.11 上存在 OpenTelemetry 依赖问题，且其 request queue/handler 形状不应泄漏到公共模型。因此首版选择 Python 自有 frontier 加 HTTPX/Playwright；只有实测证明需要持久队列、并发调度或现成拦截能力时，才增加 Crawlee 适配器。若代表性站点证明 Python 方案整体不能满足验收，再选择 TypeScript。无论结果如何，公共 JSON 契约和模块边界保持不变。

决策所需证据：

- 五类代表站点的发现召回和内容提取质量；
- HTTP 到浏览器回退是否可控；
- `onclick`、参数化子站、传统 CMS 和公开 JSON 列表的支持；
- 取消、超时、资源释放和 CDP 断线恢复；
- 依赖体积、部署难度、测试稳定性和维护成本。

## ADR-008：模块化单体优先

选择：第一版作为库在统一 API 进程中装配。只有浏览器工作负载需要独立扩缩容或故障隔离时，才拆 Worker；领域接口不随部署边界变化。

拒绝：预先拆 discovery、fetch、parse、classification 微服务。

## 重新评审触发条件

- 第二个真实项目需要不同的站点范围语义；
- Profile 无法表达的代码特例达到三个；
- 浏览器依赖显著阻碍轻量 HTTP 部署；
- 单次采集规模要求跨进程持久 frontier；
- 公共操作开始出现技术开关、调用顺序或大量透传参数。
