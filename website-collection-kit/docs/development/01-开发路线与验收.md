# 开发路线与验收

## 原则

按风险而不是按目录数量推进。每一阶段只创建实现当前用例所需的模块；不先搭满目标目录。

## 首版实现状态

截至 2026-09-04，组件已完成独立可复用的首版实现和本地验收：公共契约、URL/范围策略、robots/sitemap/RSS/HTML/DOM/JSON 发现、静态与 Playwright/CDP 获取、正文解释、证据引用、预算/取消/重定向/部分失败和覆盖报告均已落地。

统一 API 的 Job、分页传输、长期历史以及长三角业务规则仍由相邻系统负责，不属于本组件的完成范围；阶段 3、阶段 4 是宿主接入和真实站点验证计划，不代表本包内部缺少这些职责。

## 阶段 0：代表性样本与契约冻结

选择至少五类网站固定为测试样本：

- 普通静态导航和新闻详情；
- JavaScript 渲染或 `onclick` 外链；
- 参数化平台子站；
- 传统高校 CMS `/list.htm`；
- sitemap/RSS 与页面导航不一致的站点。

产出：脱敏 HTML/JSON fixture、预期路由族、页面分类样本、允许范围和已知盲区。确认 `website.discovery@1.0`、`website.collection@1.0`、`website.page@1.0` 的最小字段。

## 阶段 1：站点检查原型

实现最小 `inspect_site`：主页、robots、sitemap、HTML 链接、URL 规范化、范围过滤、分类草案和覆盖报告。用代表性网站验证 Profile 草案是否可人工理解。

验收：

- 不越过 host/path 范围；
- 能解释每个候选的发现来源或排除原因；
- 参数化子站不会因仅按域名判断而串入其它机构；
- 预算耗尽和 frontier 收敛有不同停止原因；
- 输出不宣称绝对全站覆盖。

## 阶段 2：标准内容采集

实现 `collect_site` 和 `refresh_pages`，完成标题、正文、栏目、时间、分类、证据引用和部分失败聚合。先用静态获取，再接渲染适配器。

验收：

- 普通页面无需调用方选择抓取技术；
- 动态页面可按内部策略回退且回退有上限；
- 重定向后再次执行范围校验；
- 单页失败不丢失其它成功结果；
- 相同规范 URL 在一次 Collection 中不重复产出；
- 浏览器上下文、连接和临时资源始终释放。

## 阶段 3：统一 API 接入

将公共规格映射为异步 Job，通过分页结果输出 WebsitePage。Job、游标、鉴权、配额和部署调度留在统一 API，不下沉到本组件。

验收：

- API DTO 与组件契约有显式边界转换；
- API 重复读取结果时 `record_id` 稳定；
- 取消、部分结果和最终数量可核对；
- API 不暴露 Playwright、Crawlee 或 CDP 对象。

## 阶段 4：长三角首批验证

先对少量代表站点运行并人工核对，再扩展到 49 个 high 官网。新增网站优先调整 Profile，记录需要代码策略的真实案例。

验收不只看抓取数量，还看：正文准确性、错误包含率、栏目/类型分类、时间字段置信度、外站误入、重复 URL、证据可追溯性和运行资源消耗。

## 测试分层

- 纯规则测试：URL 规范化、范围、路由匹配、分类和 Profile 校验；
- 契约测试：每个 AcquisitionPort 和 EvidencePort 实现必须通过同一套行为测试；
- fixture 集成测试：静态、动态、分页、重定向、附件和异常页面；
- 本地浏览器测试：Playwright/CDP 生命周期、取消和断线；
- 少量 live smoke test：观察真实站点漂移，不能作为唯一 CI 门禁。

必须覆盖：幂等关联、重定向越界、循环链接、参数爆炸、robots、超时、乱码、空正文、重复 canonical、浏览器崩溃和证据写入失败。

## 实现前门槛

开始写源码前必须完成：

- [ ] 确认第一批代表站点和 fixture 获取方式；
- [ ] 评审公共规格与结果字段；
- [ ] 确认 Scope 的 host/path/query 语义；
- [ ] 确认 Profile 第一版 schema；
- [ ] 用最小 spike 比较 Python 两种实现路径，并记录是否需要 TypeScript；
- [ ] 定义 AcquisitionPort 契约测试；
- [ ] 明确原始证据的最小保留形式和敏感信息清理规则。

## 防膨胀评审问题

每次新增公共类、接口或目录前回答：

1. 它隐藏了哪种调用方原本必须承担的复杂度？
2. 它是否只是把相同参数转发给下一层？
3. 它拥有独立不变量或独立变化原因吗？
4. 能否作为现有深模块的内部实现？
5. 这是两个真实用例的共性，还是单个网站特例？
6. 更换框架、浏览器或存储后，调用方是否仍需修改？

答案不清楚时不增加新公共抽象。
